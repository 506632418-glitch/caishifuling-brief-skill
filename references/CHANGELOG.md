## v1.9.8 (2026-09-29) — 板块状态机（语义层·P1）：六态 + 转换表 + 板块级回退

- 🩺 **来源**：润目贴 brief 全程实操（8 板块、含 POD2／POD3／FAQ 三次**回退**）暴露三个结构性问题——① **状态不可判定**："审核人还没回我"与"已被驳回"在 `progress` 里长得一模一样，AI 只能靠对话记忆判断，而记忆会被压缩；② **`current` 是无守卫字段**：它是**派生量**（= 首个不在 `confirmed ∪ skipped` 的序号）却独立存储，`brief_inject.py` 的 G1/G2 **完全不读它、不校验它**（`current=5` 而 `confirmed=[1,2,3,4,6]` 照样放行）；③ **回退不是一等公民**：重注入已确认板块仅 print 一句 `WARN`、不落任何记录，下游连带效应全靠人记（POD2 改「vs竞品」→ 波及板块四与 FAQ Q4，当时以"事后追认"写进 CHANGELOG）。
- ✅ **设计一｜账态分离**：**账**（事实）＝ `confirmed[]`／`skipped[]`／`pending`（新增）／`revisions[]`（新增），持久化；**态**（六态）全部由账推导，**不存储**；**删除 `current`**。理由与本用户记忆系统"派生数据不独立存储"同源——多一个字段就多一处双本账漂移的机会。
- ✅ **设计二｜六态**：⚪未开始／🟡待确认／🟢已确认／🔵修订中／⚫已跳过／🔒已冻结，各附派生依据。其中「待确认」由 `pending == N` 派生——这是本次引入状态机的**直接动因**（旧账里"待确认"与"被驳回"不可区分）。
- ✅ **设计三｜转换表 T1–T7**：为每次迁移标注触发器与守卫/落账动作。T1 呈报（G1 前序齐备 + 记 `pending`）／T2 确认（G2 未确认不许注入）／T3 驳回（须写明驳回要点，⛔不得静默进入下一板块）／**T4 重开（须审核人明示同意，落 `revisions`，`closed_at=null`）**／**T5 修订闭环（`downstream_check` 逐项裁决完毕才允许）**／T6 跳过／T7 冻结。
- ✅ **设计四｜回退语义（板块级）**：`revisions` 一条 = `{section, reason, downstream_check, opened_at, closed_at}`。**粒度＝板块级**（NOT 字段级）；`reason` **必填**且须说清"改什么+为什么"，⛔禁"微调/优化"类空话；`downstream_check` 在重开时**自动登记**为"该板块之后所有已确认板块"，闭环时**逐项裁决**（保留／同步修改／确认无影响）——**未逐项裁决不得闭环**；`closed_at` 为空即"修订中"，AI 回复须显式呈现该状态并列出待裁决项。**本质**：把"下游谁要跟着变"从**事后追认**变成**转换的必填项**，即把专家判断从"每次重新想一遍"固化为"每次被提醒一遍"。
- 📄 **落地范围（P1＝语义层）**：① `SKILL.md` 新增独立章节 `## 🔄 板块状态机（v1.9.8 引入 · 语义层）`（账态分离／六态／转换表／回退语义／与现有闸口的关系／过渡告示）；② `SKILL.md` 设计决策段新增 **决策7**（含"为什么收在板块级而非字段级"的判据：润目贴三次回退全为板块级动作，字段级收益远小于维护成本）；③ 阶段1「🧷 板块间校验锁」**接线**——读账后按状态机判态，遇未闭环 `revisions` 须先处理 `downstream_check` 再推进；④ 步骤B「progress 进度账」段补 **v1.9.8 迁移预告**；⑤ 本 CHANGELOG。**两份 references 与 HTML 工具本次零改动**（经检索：对照表／操作指南无 `progress` 引用；HTML 中出现的是进度条 UI，与账无关）。
- 🔢 **版本号三处**：frontmatter / 标题 / 版本行 → v1.9.8（日期 2026-09-29）。
- 🧭 **审核人裁决（2026-09-29）**：① `current` **删**（不接受"留字段但校验"的折中）；② 回退粒度＝**板块级**；③ 实施节奏＝**P1 先行**（先定语义、审过再动脚本）。
- ⏳ **过渡告示（重要）**：本版仅为**语义层**，**脚本与 JSON 尚未同步**——`brief_inject.py` 仍读 `progress.confirmed/skipped`（G1/G2 行为不变），`revisions`／`pending`／`frozen_at` **暂不校验**；JSON 中 `current` **暂留**（删除动作在 P3 与脚本同批执行，避免中间态不可用）。过渡期**以脚本实际行为为准**，本段只约束 AI 的判断与回复呈现。后续阶段：**P2** 脚本门禁升级（去 `current` 依赖、新增 G4 重开须有 `revisions`）／**P3** JSON 模型迁移（`+revisions` `+pending` `-current`）／**P4** HTML 六态可视化。

## v1.3.3 (2026-07-04) — 修复preload静默失败 + 清理逻辑竞态

- 🐛 **关键修复 #1**：`decodeURIComponent` hack 在特定字节序列上抛 `URIError`，导致 preload 脚本静默失败
  - **根因**：`decodeURIComponent` 对无效 UTF-8 字节序列抛异常（而非降级处理）。`atob` → binary string → `charCodeAt` → `%XX` → `decodeURIComponent` 这条链路中，某些合法 JSON 内容的字节组合可能触发此异常
  - **修复**：替换为 `TextDecoder("utf-8")` —— `atob()` → `Uint8Array` → `TextDecoder.decode()` → `JSON.parse`。`TextDecoder` 对无效字节序列降级为 U+FFFD 而非抛异常
  - 同时给 preload 脚本加 `try/catch` + `console.error`，失败不再静默
- 🐛 **关键修复 #2**：HTML 初始化清理逻辑与 preload 脚本存在竞态条件
  - **根因**：`DOMContentLoaded` 回调中 `removeItem('caishifuling_brief_v6')` 在未设置 `cleanup_done` 标记时执行——恰好抹掉 preload 脚本刚写入的数据（preload 在 DOMContentLoaded 之前运行）
  - **修复**：清理逻辑只 wipe v5，不再碰 v6

## v1.3.1 (2026-07-03) — 修复注入脚本中文乱码
